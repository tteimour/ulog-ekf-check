EKF2 Log Check

Drop a PX4 .ulg flight log. You get PX4's own EKF2 health checks: innovation test ratios, rejected measurements, numerical faults, output-predictor tracking and accelerometer vibration. The file is read in your browser and never uploaded.

What is checked, and where the thresholds come from

  • Innovation test ratios (height, magnetometer, velocity, position, airspeed, height above ground): share of in-air samples between 0.5 and 1. Warning above 5 %, fail above 50 %. Source: PX4 Tools/ecl_ekf/check_level_dict.csv.
  • Rejected measurements (estimator_status_flags.reject_*, fs_bad_mag_*): any in-air rejection fails (1 % for height above ground and optical flow). Same source.
  • Output predictor tracking error: median warning levels 8e-3 rad, 0.05 m/s, 0.15 m. Same source.
  • EKF numerical faults: any non-zero filter_fault_flags fails. Same source.
  • Accelerometer vibration: in-air peak of vehicle_imu_status.accel_vibration_metric against the 4.905 / 9.81 m/s² background bands drawn by PX4 Flight Review. Flight Review only draws the bands; grading the peak as Pass / Warning / Fail is this tool's choice.

The analysis is a TypeScript port of PX4's Tools/ecl_ekf scripts (BSD-3-Clause), with the same airtime detection: at least 5 s of flight, with 5 s trimmed at take-off and landing for height and magnetometer checks. Not ported: PX4's IMU-bias check, which reads estimator_states.states[10..15] and has not been verified against the current EKF2 state layout, and its vibration check, which reads gyro_coning_vibration. The recent PX4 logs checked during development don't contain that field, so upstream skips all three vibration metrics. Only EKF instances that log both estimator_status and estimator_status_flags are analysed.
